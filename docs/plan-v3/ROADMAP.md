## 1. 基线与方向

当前已交付的 Day 1–7：React 工作区与管理端、Go Backend、Python/FastAPI + LangGraph Runtime、按协议配置模型、DeepSeek 文本/流式/工具调用、技能偏好、只读 MCP、审批/取消、资料库、固定 CSV 分析、报告产物与历史回放。最近业务回归见 [2026-11-04 报告](../regression-2026-11-04.md)。

重构前基线 Runtime 未使用 DeepAgents，资料限 TXT/MD/CSV。当前已接入 DeepAgents、文档/网页和可选隔离计算，本地运行、浏览器、真实 DeepSeek 文档/MCP 与首个 Tavily 研究闭环证据已完成；个人长期记忆和定时任务仍未实施。既有治理与运行生命周期保留，文档技能已改为版本冻结后的按需加载。

目标是用户能交付真实工作任务、持续积累资料与偏好、授权代办事务，并在必要时使用专门分工。原型用于参考体验与功能组织，公司项目用于理解架构边界，均不作为本项目必须复制的完整功能清单。

| --- | --- | --- | --- |
| P1 通用任务助手 | 查资料、读文件、分析数据并交付结果 | Harness、实际工具、任务过程、可下载产物 | 真实材料上的完整任务闭环 |
| P2 个人工作空间 | 持续管理一个项目，复用资料、技能和偏好 | 项目、检索、个人技能、可管理记忆、产物版本 | 跨会话工作连续性与隔离 |
| P3 个人事务助手 | 管待办/日程，定时提醒，确认后代办 | 待办、日历/邮件连接、调度、通知、执行记录 | 可核查的实际事务与故障结果 |
| P4 复杂任务协作 | 必要时由研究/执行/审查分工完成任务 | 受控子代理、预算与质量评估 | 对比单 Agent 后证明有收益 |

## 2. 全阶段保持的三个决策

1. **保留现有职责边界。** Web 展示和发起操作；Backend 管身份、配置、会话/项目、文件、个人记忆、技能、连接授权与调度意图；Runtime 管 Agent 执行、运行事实、checkpoint、规范事件和工具执行记录。Runtime 的状态外置，不成为第二个个人资料或权限数据库。
2. **统一真实执行入口。** 文件、网页、MCP、代码和外部事务的真实执行必须经过逻辑 ToolGatewayService 的准入、作用域、参数校验、必要审批与审计。DeepAgents 内建工具、文件 backend 或子代理不获得绕过此边界的能力。任务计划等内部状态更新与外部副作用分开处理。
3. **按协议接模型、按证据交付。** DeepSeek 仍是首选，兼容平台复用协议适配；新的线协议另加适配器。不因模型品牌更换编排方式。实现和验证分别记录；配置页存在不代表能力打通，Mock 成功不代表真实供应商成功。

后续目标链路：

```text
Web 工作区 / 管理页
        ↓
Go Backend：身份、配置、项目、文件、技能、记忆、连接和提交意图
        ↓ 冻结的请求级上下文与权限
Python Runtime：DeepAgents / LangGraph、模型适配、计划与规范事件
        ↓
逻辑 ToolGatewayService
        ├─ Backend 作用域文件 / 记忆 / 事务 API
        ├─ 网页搜索 / 正文读取 / MCP
        ├─ 隔离 Python worker（P1-C 后）
        └─ 日历 / 邮件等连接器（P3 后）
```

个人版暂不增加 NewApi、独立 Business Gateway、独立 Tool Gateway 服务、Kubernetes 或向量数据库服务。达到实际的多渠道治理、扩容或检索要求后再评估。

## 3. P1：通用任务助手

### 3.1 用户目标

用户用自然语言交代任务，助手选择已经授权的工具，读取材料或查询网页，形成有依据的结果，并能继续修改产物。

例子：上传两份材料后要求“找出变化，整理风险，输出一份对比报告”；或“研究一个主题，比较几种方案并附来源”。

### 3.2 功能与实施批次

| 批次 | 必须交付 | 依赖与范围 |
| --- | --- | --- |
| P1-A 执行底座与第一个任务闭环 | DeepAgents 兼容版本、模型桥接、规范事件桥接、现有工具接入、审批/取消不退化；网页搜索与正文读取；带来源的 Markdown 报告；首页重排 | 下一轮 5–7 天窗口的建议范围。先保留现有文件格式；不同时加入代码沙箱、长期记忆、复杂子代理 |
| P1-B 文件工作能力 | 文字型 PDF、DOCX 解析；按段/页读取与关键词查找；受控创建/修改工作文件；报告版本与下载；长对话压缩、任务进度与资料引用 | 依赖 P1-A 稳定。扫描件 OCR、旧 DOC、复杂版式还原和图片理解不在首批 |
| P1-C 计算与正式产物 | 现有结构化 CSV 计算向通用任务接入；固定依赖的隔离 Python；XLSX 基础读取；图表和 DOCX 报告生成 | 先完成隔离执行、超时/资源/网络限制与文件输入输出契约，才开放生成代码运行 |

**任务执行体验：** 展示待处理/进行中/完成/失败的工作步骤、当前工具和最终产物；简单聊天不强制列计划。显示的是任务过程和证据，不展示隐藏推理。失败时保留已有结果，说明缺失材料、工具错误或预算耗尽。

**网页工具：** 搜索必须使用真实可配置的搜索服务或已接通的搜索 MCP；只有 URL 抓取不能称为联网搜索。返回标题、地址、读取时间与可引用段落。正文读取限制重定向、目标地址和内容大小，不携带用户浏览器登录态；暂不承诺登录后网站、验证码或全站爬取。

**文件工具：** 仅能读本次授权文件和工作区路径；读取支持分页/截断提示。文件内容与网页属于外部材料，不赋予执行权限。工作文件通过 Backend 的作用域 API 读写，不能直接挂载或读写 Backend 的整个文件卷。修改产生新版本，不覆盖用户上传原件。

**计算工具：** 能由结构化参数完成的统计继续用确定性代码；确需动态 Python 时才使用 worker。只复制授权输入文件，限制 CPU/内存/时长/输出量，默认无网络，不挂载宿主目录或 Docker socket。Runtime 不直接获得宿主机 shell。首版限制固定依赖和任务类型，Docker 容器的存在不能单独作为任意不可信代码执行已安全的证明。

**上下文管理：** 长工具结果落工作文件，prompt 只放相关片段和索引；达到阈值压缩早期内容，保留任务目标、用户约束、来源引用、已完成动作和待审批事项。历史原文保留，摘要不是新的业务真相，也不承诺无限上下文。

### 3.3 Harness 迁移设计

- 先核对并锁定兼容的 DeepAgents / LangChain / LangGraph / checkpointer 组合，不把公司版本或在线文档示例直接当成本项目兼容性结论。
- 模型接口增加满足所选 Harness 的桥接层；复用现有协议选择、凭据别名、受控选项、流式过滤与预算逻辑。框架默认模型客户端不能绕过这些边界。
- DeepAgents 的流事件翻译为本项目规范事件，Web 不直接绑定其内部消息结构。最终回答继续去重，刷新/断线补读继续有效。
- 工具仍冻结于一次 Run 的授权快照。框架文件工具通过自定义 backend 接入现有治理；首批显式关闭未接入的默认 shell、写入和子代理能力。
- 只有一套审批事实：Backend 保存决定，Runtime 验证后恢复；框架 interrupt 作为等待机制适配，不能同时再生一套独立批准记录。参数改动、过期或权限修订必须重新提案。
- 为运行增加 engine/checkpoint 版本绑定。旧完成历史保留可读；旧审批等待 Run 先用旧引擎收敛或显式结束后重发，不直接把旧 checkpoint 当作新图状态反序列化。
- 更新时保留回滚镜像和兼容数据结构。回滚只影响后续可接收任务，不自动重跑已经执行过的工具，也不让新引擎 Run 被旧引擎误接管。
- 首批使用单主 Agent。轻聊天可以采用无工具/少中间件的执行配置；不长期维护两套平行的自研工具循环。

### 3.4 UI 对齐

- 首页：简洁欢迎语 → 中央输入框 → 真实可用的任务/技能卡片；已有会话仍为底部输入框。
- 统一文本对比度、边框和间距，减少渐变与装饰性标签；当前模型和工具选项折叠在输入区。
- 会话页：正文为主体，任务步骤与工具结果可折叠；审批明确展示动作和参数；右侧产物可预览、下载和继续修改。
- 首批补会话搜索/日期分组，自动标题采用规则回退或复用已有结果，不为标题默认额外付费调用模型。
- 保留已有数据分析页，本轮不做其模块重构；之后从聊天入口逐步复用计算能力。

### 3.5 阶段完成验收

1. 上传两份真实的文字型 PDF/DOCX，比较内容并生成可下载报告；关键结论可定位到文件页码或段落，修改要求产生第二版。
2. 对一个主题进行真实搜索并读取多个来源，输出引用可打开、内容能对应的报告；来源不可用时明确标注，不编造引用。
3. 用上传 CSV 完成聚合、图表和说明，数值由计算结果决定；不能用模型编造数值代替执行。
4. 长任务能显示步骤、取消并保留产物；越权文件读取、超时、工具失败、重复提交和审批恢复有清晰结果。
5. 现有首版回归不退化；P1-C 额外验收隔离执行边界。测试与真实模型调用均按授权执行。

P1-A 单批完成不等于整个 P1 完成。第一批证据至少包括一次完整研究任务和原有工具/审批链路的兼容结果。

## 4. P2：个人工作空间

### 4.1 用户目标

围绕一个持续项目工作，而不是每次重新上传材料、解释背景、粘贴格式。跨会话保持可管理的连续性。

例子：“这是我的产品项目，使用这些资料，记住周报结构，以后每次按这个结构更新。”

### 4.2 功能与实施批次

| 批次 | 必须交付 | 首批边界 |
| --- | --- | --- |
| P2-A 项目与检索 | 个人项目、项目说明、绑定会话/文件/产物；历史与资料全文检索；来源引用；收藏/归档/回收站 | 一个资源有明确 owner 和所属项目，不能只靠前端过滤 |
| P2-B 个人技能与记忆 | 个人技能创建/编辑/版本/启停；把成功任务整理成技能草稿；明确记住、修改、忘记；记忆列表和调用说明 | 草稿由用户确认保存；不做静默自我进化、不自动保存所有聊天 |
| P2-C 产物连续编辑 | 版本链、版本说明、来源会话、基础差异、指定版本继续加工 | 先做文本/报告；复杂办公文档实时协同编辑另列 |

**项目：** 默认有个人收件区，用户无需先建项目才能聊天；需要持续工作时再归入项目。项目说明由 Backend 管理，选中项目才下发相应背景。

**检索：** 初版用现有 PostgreSQL 的文本索引、关键词/片段检索，覆盖文件标题、已解析正文和授权会话。验证中文检索效果与规模后，确有必要再增加 embedding/pgvector；嵌入提供方和费用另列，不因使用 DeepSeek 聊天模型就假设已有 embedding 服务。

**个人技能：** 保存目的、适用情景、步骤、输出模板和所需能力说明；预览后确认保存为版本。平台技能与个人技能分开授权，个人修改不影响其他用户。按任务需要加载正文，不全量塞入 prompt。技能引用工具不等于授予工具权限；首版个人技能不带任意可执行安装脚本。

**个人记忆：** 优先记输出偏好、常用格式和项目背景，不主动收集敏感身份信息。每条记录保存来源、作用域、更新时间、有效状态；用户能查看、更正、删除与关闭使用。本轮明确要求优先于项目偏好，项目偏好优先于个人通用偏好；冲突或不确定时询问，不自行覆盖。

“忘记”使后续记忆检索与拼装不再使用该条记录；删除记忆不等于删除历史消息、既有产物或备份，相关入口需要分别说明。每次 Run 绑定所用记忆版本，缓存随删除/更新失效，不能下一轮继续注入旧内容。

### 4.3 架构与数据

- Backend 新增项目、项目资源关联、个人技能/版本、记忆/来源、产物版本等业务对象；仍在本项目自身 schema 内，不借用公司数据。
- Runtime 在请求级获取授权内容和记忆检索结果；记忆写入作为受控请求发往 Backend。图摘要、临时笔记、个人记忆三者分开，不重复作为长期事实保存。
- 检索在返回片段前完成用户/项目过滤；不能先跨用户检索再让模型自行判断归属。
- 文件删除/回收、重新解析、技能编辑和记忆变更都有 revision/失效机制；产物和历史引用明确显示已删除来源。

### 4.4 UI 与验收

UI 增加项目切换、项目资料、个人技能、记忆管理和产物版本入口；默认保持简洁，按需要展开。资料库从单一文件列表变成可查找、可复用的工作资料入口。

完成标准：

1. 在项目 A 新建会话可以检索 A 的材料；切到 B 不自动携带 A 的资料与偏好，另一用户无法访问。
2. “记住我的周报用进展/问题/下周计划三段”经确认保存；新会话复用；修改和忘记后下一轮立即体现。
3. 从一次成功任务生成个人技能草稿，经用户保存后能再次运行；停用后不自动加载，旧版本记录仍可追溯。
4. 报告从 v1 更新为 v2，能打开两版、理解修改点并从指定版本继续；删除来源不导致权限绕过。

## 5. P3：个人事务助手

### 5.1 用户目标

从给建议进一步做到管理待办、安排日程、定时提醒，以及经确认执行真实动作。

例子：“明天上午十点提醒我整理周报；每周五根据这个项目的材料生成周报草稿；帮我拟一封会议邀请，确认后再发送。”

### 5.2 功能与实施批次

| 批次 | 必须交付 | 首批边界 |
| --- | --- | --- |
| P3-A 自有待办与调度 | 待办创建/更新/完成；一次性提醒与周期任务；时区、暂停、下次执行、站内通知、执行记录 | 先做站内提醒和草稿生成。电脑/服务关闭时无法准时执行，必须说明 |
| P3-B 第一条外部连接 | 按实际使用选择一家日历或邮件服务；授权/撤销、读取/搜索、创建草稿、确认执行、结果核查 | 先打通一个实际账号，不同时宣称支持所有邮箱/日历 |
| P3-C 受控自动化 | 触发条件 → 授权材料与技能 → Run → 通知/审批；失败重试、暂停、预算上限 | 先是定时/手动触发；复杂可视化流程编辑器和任意事件总线后置 |

**授权体验：** 初次连接说明能读取什么、能修改什么；授权状态、到期、撤销入口可见。用户可选择更小的范围；只读授权不能默认为可发送邮件或修改日历。

**事务体验：** 先展示草稿和关键字段，如收件人、标题、时间、时区、内容和附件。修改后旧批准失效。执行后显示外部对象 ID、可查看入口与结果，不以“模型说已发送”作为成功。

**调度体验：** 保存用户时区和下一次执行时间；明确错过触发是跳过还是补跑、最多补跑几次。用户可暂停/删除任务，查看各次结果。低风险草稿生成可按已确认配置定时运行；向外发送或修改默认保留审批，不默认长期授权所有动作。

**本地能力：** 如确需读取电脑目录或使用本地登录态，另做范围受限的本地连接/执行代理，由用户选择目录和用途。不让云端 Runtime 直接访问整台电脑；完整 Tauri 桌面端和通用浏览器自动操作不作为本阶段前置。

### 5.3 架构与可靠性

- Backend 管连接授权元数据、任务定义、通知、触发意图和事务结果；凭据独立加密保存或通过部署秘密服务引用，不进入模型消息、事件或 checkpoint。
- 调度采用独立 worker 进程和 PostgreSQL 租约/锁，可复用 Backend 代码但不把长期等待放进 Agent loop。仅在实际吞吐需要时增加队列设施。
- 每次触发产生唯一 invocation/submission，通过已有入口派发 Runtime；触发次数与 Run 状态分开。
- 外部动作保存 execution_id、参数摘要和外部结果。网络超时后优先查询/对账；只有可证明安全才重试。外部不支持幂等与查询时保留 UNKNOWN，不承诺全局 exactly-once。
- 定时触发视为至少一次投递，通过唯一触发键去重。取消不能撤回已经送达的邮件或已经提交的外部写入。
- 模型额度、运行时长、触发频率、站内通知与真实外部动作分别限额；自动化不绕过模型调用预算。

### 5.4 完成验收

1. 提醒在指定时区触发，页面显示记录；暂停后不再新触发；重启、漏触发的行为符合配置。
2. 周期生成草稿并发站内通知；重复触发不产生重复同次任务，失败有原因和重试记录。
3. 在隔离/受控账号中完成真实日历创建或邮件发送；用户拒绝时外部无写入，参数改变必须重新确认。
4. 模拟响应丢失、凭据撤销、授权到期和预算耗尽，结果不能伪装成功或盲目重复发送。

## 6. P4：复杂任务协作与质量提升

### 6.1 用户目标

对足够复杂的任务，专门分工能提高质量或缩短耗时，同时保留单 Agent 的简单路径。

例子：“研究三种方案，做一份基于真实数据的对比报告，检查数值与引用，再提交最终版。”

### 6.2 功能与实施批次

| 批次 | 必须交付 | 首批边界 |
| --- | --- | --- |
| P4-A 固定分工 | 主 Agent + 研究助手 + 执行助手 + 审查助手；任务契约、分工过程、结果汇总、子任务取消 | 先固定角色、按需要委派，不先做用户自由搭建智能体商城 |
| P4-B 质量与资源治理 | 总预算、并发/深度/超时；来源和计算验证；回归任务集；与单 Agent 对比 | 先记录真实耗时/调用/结果；模型自评分不能单独作通过依据 |
| P4-C 按需扩展 | 分角色模型选择、有限动态委派、必要的后台长任务；后续再评估专业专家与远程 Agent | 有证据证明收益后启用；不预先引入无限递归、A2A 或复杂分布式调度 |

### 6.3 分工与执行约束

| 角色 | 工作范围 | 能力边界 |
| --- | --- | --- |
| 主 Agent | 澄清目标、拆分任务、汇总并向用户交付 | 决定是否委派；不把未经核查的子结果直接当最终事实 |
| 研究助手 | 搜索、阅读、摘取证据和引用 | 只读；返回来源和未确认点 |
| 执行助手 | 计算、文件加工、产物生成 | 在授权工作区/沙箱执行；真实写入仍需相同治理 |
| 审查助手 | 检查约束、引用、数值和交付物 | 只读；输出问题和修订建议，不自行改外部系统 |

- 子任务有 parent_run/task_id、目标、输入、工具范围、完成条件和结构化输出。只接收必要上下文，不继承全部历史、所有记忆和凭据。
- 子权限是父任务授权范围的子集，委派不能扩权；共享一套预算与审批规则。
- 初版建议每个主任务最多两个并行子任务、一层委派，均为可调策略，不是性能承诺。父任务取消向下传播，并记录无法撤回的已完成动作。
- 优先隔离临时工作区；共享产物采用显式发布和版本检查，避免子任务互相覆盖。
- 并发工具提案进入受控审批队列；已有“一 Run 一个待审批”限制需显式扩展或串行化，不能让并行任务覆盖待审批记录。
- 保存规范的父子运行关系和事件；Web 展示任务树与结果，不展示内部推理。Runtime 仍不保存长期控制面配置。
- 不做“多个模型互相说通过就通过”的审查：数值以实际计算为准，来源以可定位内容为准，文件以可打开的交付物为准。

### 6.4 完成验收

1. 同一复杂任务由研究、执行、审查分工，最终报告包含可核查来源、真实图表和审查后修订。
2. 简单问题不无故启动多个子代理；子任务失败时主任务能解释影响，不能伪造完整完成。
3. 总预算、并发、超时、权限和取消在父子任务间生效；出现部分成功能如实呈现。
4. 对固定任务集比较单 Agent 与多 Agent 的正确性、完整度、耗时、模型/工具调用与成本；没有收益的任务继续使用单 Agent。

## 7. 统一验收与交付约定

每个批次在实现前冻结输入、输出、业务对象、规范事件、工具范围、失败行为与完成标准；跨层变化先更新 schemas/OpenAPI/共享样例，再改 Go/Python/TS。

每批提供：

- 一条用户可实际完成的成功链路，以及至少一个与新增能力相关的失败闭环。
- 已实现/未实现清单、迁移和回滚说明、操作入口与限制。
- 授权执行后记录的证据；未运行的项目明确“未执行”。新增评估优先覆盖多步行为、权限、恢复和真实产物，不堆叠实现细节测试。
- 单独列出模型供应商、工具服务、embedding、邮件等外部依赖与费用；没有实际配置的连接显示不可用。

本次仅阅读代码/文档并制定规划，没有运行测试、安装依赖、迁移数据库或调用模型。既有真实模型验收额度已经用完，本规划不产生新的真实调用授权。后续测试默认不主动运行；用户明确要求验收时按该次授权范围执行，真实调用另明确请求数、输出上限与费用范围。
