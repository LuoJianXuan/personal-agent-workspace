# 第一阶段详细重构计划

后续实施方向已收敛到 [Personal Agent优化方案](PERSONAL-AGENT-OPTIMIZATION.md) 与 [决策007](../decisions/007-personal-agent-harness.md)。本文保留原重构与验收规格，不作为继续扩张企业部署或新增文档常驻服务的依据。

计划日期：2026-11-05；验收更新：2026-11-06。S08–S20代码齐备，本地隔离业务/故障/浏览器/真实Docker运行通过；真实 DeepSeek 文档/MCP 工具链已补充验证，真实搜索和日常切换/完整回滚待验证。见 [本次验收](../phase1-acceptance-2026-11-06.md) 与 [交付说明](../phase1-refactor-delivery.md)。

适用项目：独立 agent-workspace。遵守 AGENTS.md 与 [框架优先决策 006](../decisions/006-framework-first-harness.md)。不修改公司灵机 AI，不复制公司实现；本文保留实施与验收规格，不能据此推定验收已通过。

本文细化 [第一阶段执行方案](PHASE1-EXECUTION.md) 的重构顺序，仍使用 S08–S15 编号。核心底座重构集中在 S08/S09，S10/S11 接网页研究和 UI，S12–S15 在新底座上补文档、上下文与计算，不与底座迁移同时大范围改写。

## 1. 重构目标和三个决策

目标：把现有手写 Agent 图替换成实际 DeepAgents 主 Agent，使用标准模型集成、官方中断恢复与限次机制；自有代码集中在授权、业务幂等、运行协调、文件和产品事件。

1. **替换通用机制，删除旧实现。** 不让新 Agent 外再运行旧 StateGraph，不长期维护两个模型流解析器、两个工具循环或两个审批恢复流程。
2. **保留必要产品能力。** 身份、会话、运行提交、规范事件、历史、文件、审批决定、取消、写入幂等与总额度继续存在；通过薄集成接入框架。
3. **先达到兼容门槛，再新增能力和切换环境。** 先证明已有功能在新底座成立，再接搜索/文档/计算；未验收时不替换日常 Runtime。

“一套执行机制”不等于删除全部状态：LangGraph checkpoint 保存执行进度，Runtime Run 记录对外生命周期，Backend 保存提交意图和用户决定。各有职责，但不能各自再驱动一套 Agent loop。

## 2. 完成后的结构

```text
Web：聊天、审批、来源、产物
  ↓ 既有 Backend API / SSE
Go Backend：身份 / 配置 / 会话提交 / 文件 / 审批决定
  ↓ 请求级上下文与授权快照
Python Runtime
  ├─ Engine：接收、排队、取消协调、运行终态
  ├─ Harness：实际 create_deep_agent + 官方中间件 + checkpointer
  ├─ Models：协议配置 → 标准 ChatModel + 必要传输限制
  ├─ Tool policy/provider：治理规则与真实工具执行
  ├─ Approval binding：产品审批记录 ↔ 框架中断
  └─ Event bridge：框架事件 → 持久规范事件
```

新增模块以实际职责为准，不预建插件平台、通用执行 DSL、抽象工厂层级或微服务。A 不增加 NewApi、Business Gateway、独立 Tool Gateway、Redis 或向量数据库。

## 3. 逐模块替换、保留和删除清单

| 模块 | 采用的实现 | 必须保留 | 删除/收敛目标 | 结果核查 |
| --- | --- | --- | --- | --- |
| engine.py | DeepAgents 驱动执行 | accept/排队/终态、外置 Run、取消与容量 | 手写 model/prepare/approval/execute/merge 图节点与边；重复轮转 | 一个 Run 只启动一个 Agent 执行 |
| models.py | 经核对的标准 LangChain ChatModel | protocol→客户端、允许地址/选项、凭据、必要错误/正文过滤 | 可被替代的 SSE 行解析、工具参数碎片合并、重复消息协议 | SDK 实际请求仍受到本项目限制 |
| tool_gateway.py | 标准工具 + 治理中间件/受控 provider | owner/revision/作用域、目标准入、审计、execution_id/幂等 | 第二套工具调度；散落在 Engine 的执行判断 | 每次真实执行都能追溯准入与结果 |
| approvals.py | 官方 HITL/checkpointer/Command 恢复 | 参数绑定、有效期、归属、Backend 决定核验 | 对特定图节点名的依赖、独立 interrupt 节点与重放流程 | 一次批准只恢复同一提案一次 |
| 流式/事件 | 官方流事件 + 一个产品事件转换入口 | canonical event、游标、去重、历史投影、脱敏 | 自研供应商事件解析、重复 final producer | 实时、刷新、历史均为同一份最终结果 |
| 预算 | 官方模型/工具限次 + 实际请求硬额度 | 授权总请求数、输出上限、用途与实际用量记录 | Engine 中依赖手写循环步数的计数 | 摘要/重试不绕过，审批恢复不重置 |
| 取消 | 底层异步执行 + 外层业务协调 | 持久请求、工具/worker 传播、终态和对账 | 只取消 UI、只停 SSE 或多处互相覆盖状态 | 请求停止与执行已停止可区分 |
| materials.py / MCP | 现有确定性能力包装为标准工具 | 实际 MCP、Decimal 统计、文件验证、产物存储 | 为适应旧图而做的消息拼装和重复编排 | Mock 模型也调用这些真实模块 |
| Backend / Web | 保留现有服务和业务页面 | 登录/权限/配置/文件/审批/历史/管理入口 | 仅清理确已失效的旧契约耦合 | 不因底座重构丢掉产品能力 |

删除以依赖核对和对应行为验证为前提。不能为了删代码移除鉴权、审计、幂等或原有业务契约；必要兼容补丁应写出问题、影响范围与删除条件。

## 4. 执行顺序与任务包

### R01 / S08：固定基线和不变行为

**步骤：**

1. 记录实际源码/锁文件/镜像标识；无可用 Git 时使用排除秘密的源码 SHA256 清单，不虚构 commit。
2. 列出既有接口、状态、3 个内置工具与只读 MCP、实际故障用例，形成重构前后行为对照表。
3. 列出需兼容的 9 项行为：聊天、多轮、MCP、工单审批、取消、流式补读、离线历史、资料/CSV、产物下载。
4. 在已授权环境核对在途 Run；准备本项目数据/文件备份与恢复办法。此步骤不修改运行状态、不清空卷。

**交付：** baseline manifest、行为对照表、影响文件清单；任何既有局限沿用原说明，不能在重构后被误称为已解决。

### R02 / S08：依赖、契约和迁移方案

**步骤：**

1. 按 Python 3.13、标准模型客户端、DeepAgents/LangGraph/checkpointer 核对兼容组合，更新并锁定依赖；不直接照搬公司版本或当前在线示例。
2. 为每项自研机制记录“框架入口 / 保留规则 / 待删代码 / 验证用例”，先识别缺口再实现适配。
3. 冻结引擎版本、事件兼容、工具策略、HITL 绑定、恢复和调用预算契约。先改 schemas/OpenAPI/样例，再生成 Go/Python/TS。
4. 确认框架构建后的实际工具清单；A 关闭尚未受控的默认文件/命令/子代理/自动记忆能力。
5. 为新 saver 选择独立物理表空间，必要时使用 Runtime 专属 schema。只有 checkpoint namespace 不足以隔离 saver 表结构升级。

**交付：** 兼容矩阵、采用/删除矩阵、共享契约、非破坏迁移及回滚说明；无法确定兼容性时明确阻断后续，不靠猜测继续。

### R03 / S09：替换主 Agent 和模型

**步骤：**

1. 新增小型 Harness 装配入口，实际调用 create_deep_agent；Engine 只负责启动/协调，不再驱动旧图。
2. 按 protocol 构建经验证的标准 ChatModel。provider 标签不选择适配器；只开放已有协议和受校验选项。
3. 核对 DeepSeek 非思考模式的受控参数、工具调用和真实流行为；保留必要过滤，避免把未知参数全部透传。
4. 使用同一受信 HTTP/传输边界限制目的地址、凭据和物理请求；SDK 不可绕过授权额度或偷偷自动重试。
5. 为验收实现符合框架模型接口的确定性 MockChatModel，能够产生正文、工具请求、分块、中途失败；不得以假 Agent 或假工具替代真实链路。
6. A 暂不启用依赖 B 文件 backend 的自动外置/摘要；启用时必须进入统一预算与作用域。

**交付：** 实际主 Agent、标准模型构建、受控 Mock；移除可替代的旧模型协议处理。未执行真实请求时不标 DeepSeek 新底座已验证。

### R04 / S09：收敛工具执行与审批

**步骤：**

1. 将查单 MCP、资料读取、固定 CSV、演示工单注册为标准工具；工具目录由服务端快照生成。
2. 工具参数定义复用权威 schema。框架负责通用参数结构，网关保留业务归属/hash/revision/审批和幂等校验；不能维护两份不同的字段规则。
3. 工具包装只依赖请求上下文、Backend 客户端、事件写入与治理接口，不再把整个 Engine 当作所有工具的隐式依赖。
4. 演示工单优先采用官方 HITL，仍由 Backend 保存批准/拒绝和审计。当前 UI 不开放 edit；参数变化须生成新提案。
5. 将框架中断与稳定的业务 approval_id、execution_id、参数摘要、权限版本和有效期绑定；优先使用稳定工具调用标识，若框架字段不同，S08 须验证可持久重建的映射。
6. 不再判断 state.next 必须等于旧 approval 节点；确认 checkpoint 中存在真实等待点后才发布待审批状态。
7. 批准后先核验原决定再恢复同一图；实际写入前再次检查权限/过期/参数绑定，沿用 Backend 工单幂等和结果查询。
8. 一项工具只有一个审批裁决来源。A 只做实际需要的路径；将来由治理层裁决 approval_required 时，使用薄中断适配并排除重复 interrupt_on。

**交付：** 原有批准/拒绝/到期/取消/重启边界成立，最多一张工单；移除旧手写审批图和重复恢复驱动。旧审批表保留历史，新记录不得再成为并行执行状态机。

### R05 / S09：统一流式、事件与历史

**步骤：**

1. 从框架标准消息、工具、计划和 interrupt 流生成产品规范事件；不让 Web 直接消费框架内部对象。
2. 建立唯一 message_id/chunk_index 映射和最终正文收敛点；中间工具前文本、最终回答与隐藏推理明确区分。
3. 继续由 Runtime 持久化关键事件，Backend 代理并幂等投影历史；不把 checkpoint 或 UI 状态另存成第二份历史事实。
4. 保留 after_seq 重连、慢订阅限制、心跳与离线历史回退。关闭浏览器或 SSE 断开只影响订阅，不自动停止 Run。
5. 关键审批/写入/产物事件失败须中止相应后续动作或进入可对账状态；不发布尚未持久确认的“已批准/已完成”。

**交付：** 生成时逐步可见，刷新后补读，最终回复一份；Runtime 不可用时已保存历史仍可阅读。

### R06 / S09：取消、限额与运行协调

**步骤：**

1. 保留 Backend 的持久取消意图，经现有命令转给 Runtime；将信号传递到活动模型任务和工具 worker。
2. 区分“已收到取消”与“执行已停止”；对无法撤回的写入查询并保留真实结果，不宣称自动回滚。
3. 官方模型/工具限次用于限制执行规模；实际请求边界负责本次授权额度，统一覆盖自动重试、辅助/摘要模型和输出上限。
4. 保留业务 thread_id 与 graph thread 的既有含义：一次业务 Run 对应自己的图持久标识。核对官方 run_limit 的 invoke/resume 范围，恢复后不重新获得一份额度。
5. 容量/排队、恢复占槽、终态 CAS 和错误映射保留薄协调；不新增调度平台。模型中断后的 usage 不完整须标记，不伪造精确费用。

**交付：** 取消可追踪、恢复不超额、调用次数不被 SDK 隐藏；原有单 thread 活跃约束和容量边界不退化。

### R07 / S09→S11：兼容门槛、旧代码清理与切换

**步骤：**

1. 准备既有验收入口在新模型接口下的适配，按行为验证，避免测试只依赖旧类名/节点名。
2. 先在独立 verification 工程按授权执行兼容用例；真实模型、真实搜索、浏览器分别按该次授权范围进行。
3. 对照采用/删除矩阵清理未使用的图节点、旧 parser、重复审批驱动、临时切换代码和相关失效依赖。
4. 旧日常服务继续接收/收敛旧任务；切换窗口先停止接受新提交，等旧在途和待审批任务收敛，或按用户授权显式结束。
5. 升级后的新镜像只承担新引擎执行，不长期携带旧循环。旧镜像与数据用于回滚，不靠把新 checkpoint 塞给旧图来兼容。
6. 旧历史、文件和证据保留。新旧协议消费者按版本协同发布，通过服务端开关启用新执行；不能只替换 Runtime 后假定旧闭合 schema 会接受新字段。
7. 回滚前先处理新引擎在途任务；回滚是停止派发并恢复已确认兼容的旧镜像/入口，不重放未知副作用、不破坏性降库。

**交付：** 行为兼容证据、旧实现删除清单、迁移/回滚记录。未获得测试授权或门槛未满足时保持“代码齐备/待验收”，不自动覆盖日常 Runtime。

## 7. 验收标准

### 7.1 底座兼容的九项行为

| 行为 | 必须证明的结果 |
| --- | --- |
| 聊天/多轮/技能 | 实际经新 Harness，选择/启停语义不变，最终文本一份 |
| 只读 MCP | 真实模块查单，有执行记录；禁用/撤权后不执行 |
| 工单审批 | 参数完整、批准/拒绝/过期/变化正确，同一执行最多写一次 |
| 审批重启/恢复 | 确认等待点可恢复；错误版本/已过期决定不误执行 |
| 流式/重连 | 正文实际增量、游标补读，不暴露隐藏推理/工具参数碎片 |
| 历史/离线 | 旧完成记录仍可读；Runtime 离线不抹掉持久最终回答 |
| 取消 | 排队/模型中/审批中可处理，已写入结果保留真实状态 |
| 文件/CSV/产物 | 作用域不越权、数值可复算、下载鉴权和幂等有效 |
| 预算/容量/幂等 | 重试/恢复不重置额度；双提交不双 Run；队列与订阅边界继续成立 |

### 7.2 精简本身也要验收

- 实际使用 create_deep_agent，原通用图节点与轮转已移除。
- 标准模型客户端实际工作，旧供应商 parser 仅在有证据的必要缺口中保留。
- 一项工具一个审批裁决来源，没有两次批准或两套恢复驱动。
- 一处规范事件转换与最终消息收敛点，没有双份最终回答。
- 一个业务 Run 的额度在所有 invoke/resume/辅助调用中一致。
- 产出代码变更与删除清单、依赖变化和耦合关系说明；不以单纯行数或文件数作为成功标准。

### 7.3 分开记录实现和验证

实现状态：未开始/实现中/代码齐备/需修复。验证状态：未执行/静态核对/运行通过/运行失败。

每个 Spec 交付 docs/evidence/SXX.md：实际改动、契约、迁移、成功和失败链路、已执行证据、未执行项、边界与下一步。Mock 仅替换模型，不替换审批/MCP/数据库/文件；网页 fixture 不作为真实联网证据。

现有授权真实模型额度已用完，本规划不增加额度。默认不运行测试、浏览器自动化或真实调用；后续明确授权验收时执行相应层次，真实请求须有次数、输出上限及服务范围。不拿旧验收结果替代重构后的验证。

## 8. 关键失败窗口

**批准后工具写入成功，但模型/Runtime 随后中断。**

保持稳定 execution_id，先查询 Backend 原结果；确认已写入就复用，不因框架重放工具或客户端重试而再写。Run 可以显示中断/失败，同时展示真实已完成动作。取消也不能自动撤回该动作。

这是重构兼容的硬门槛：框架恢复方便不能成为重复执行真实副作用的原因。

## 9. 可以直接下发的首个实施范围

执行 S08（R01/R02）：读取本计划、006 与现有架构，固定基线，核对依赖，完成采用/删除矩阵、契约与迁移设计，接入三端共享生成产物并准备兼容验证入口。保持独立项目与服务边界，不主动使用子代理，不默认运行测试或真实调用；在 S08 证据中明确代码/验证状态及阻塞依赖。S08 结束后进入 S09，不把整套 P1 一次性混改。

框架能力依据沿用 006 中的官方模型、HITL、中间件、流式与持久化文档；具体版本/API 在 S08 核对，不把在线版本当成已安装组合。
