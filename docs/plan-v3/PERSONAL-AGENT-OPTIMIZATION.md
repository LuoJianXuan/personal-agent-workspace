# Personal Agent 优化方案

日期：2026-11-06。状态：S16–S20代码齐备并完成本地隔离运行验证；真实 DeepSeek 的 DOCX/MCP/公网研究工具链、独立 `Personal Agent Demo` Langfuse Project/Key 调用树入库与故障旁路均通过；当前版本已切换日常 5173。用户撤销演示数据备份/回滚交付项。详见 `docs/evidence/S16.md` 至 `S20.md`。

产品目标：面向个人的通用智能助手，帮助用户围绕文件、网页、数据及后续个人事务完成任务。以单主Agent和精简Harness为基础，能力通过工具/技能组合；不以完整企业平台或资料入库系统为默认形态。

依据：[一手资料调研](../research/personal-agent-document-processing-2026-11-06.md)、[决策007](../decisions/007-personal-agent-harness.md)、[框架优先决策006](../decisions/006-framework-first-harness.md)。本方案在实现方式上优先于旧S12的“独立常驻文档worker”设计，旧代码与验收仍是历史事实。

## 1. 三个关键决策

1. **保留DeepAgents，参考Pi思想。** 不再替换运行底座；继续用框架循环、文件接口、上下文整理和原生审批。主Agent只装配模型、当前工具、上下文与扩展，不为每项功能新增编排层或专用子Agent。
2. **默认按需执行，减少必需部署。** 文档读取改为工具触发固定解析；普通固定提取运行在Runtime管理的受限子进程中。复杂/生成代码仍走已有可选Docker设施。共享的是生命周期和执行约束，不把两种执行方式包装成新的微服务框架。
3. **保留已有业务结果，收窄观测。** 文件授权、hash、来源定位、工作文件、报告版本、取消/限额/审计不退化。Langfuse只接Agent、模型和工具回调，不加入HTTP全链路、排队、worker、容器内每阶段观测。

## 2. 本轮范围和不做项

本轮窗口为5–7个工作日，范围固定为文档处理收敛、最小技能按需加载和Agent调用追踪。后续真实供应商验证与日常发布仍按现有授权和门槛处理，不因工期而宣称通过。

本轮保留支持：UTF-8 TXT/MD/CSV、文字PDF、DOCX、基础XLSX；文档比较、来源、MD/DOCX/CSV/Chart产物、报告新版本；既有MCP、审批、取消和回放。

本轮不新增：完整Word原位编辑套件、扫描OCR、原生WPS/旧DOC/PPT兼容、通用PDF转换与排版认证、任意宿主shell、自动安装任意技能脚本、技能市场/插件市场、长期记忆、定时任务或多Agent编排。格式扩展和事务能力应复用本轮执行方式，后续单独冻结任务范围。

## 4. 目标结构

```text
Web
 ↓
Backend：身份/会话、文件与授权、缓存/产物/版本
 ↓
Runtime：一个DeepAgents主Agent
 ├─ 框架上下文、流式、取消、原生审批
 ├─ 当前可用工具 + 技能摘要/按需读取
 └─ 逻辑工具准入
       ├─ 文档/表格固定函数 → 受限子进程（按需启动）
       ├─ 工作文件/网页/MCP → 现有受控接口
       └─ 生成Python → 已有可选Docker执行器

官方CallbackHandler → 既有Langfuse个人Project（可关闭、旁路）
```

`execution.py`作为Runtime内部模块复用子进程启动、超时、取消、输出限制与错误转换；Docker调用仍委托现有broker。它不提供独立HTTP服务，不替换DeepAgents工具循环，不引入通用调度平台。模块数量允许随职责变化，部署服务数不随功能名增长。

## 5. 一条实际任务的目标链路

任务：“对比这两份合同，列出修改与风险，生成Word报告。”

1. 上传原件：Backend验证类型/大小、保存不可变文件与hash，立即返回。不会自动解析全部二进制文件，也不调用模型。
2. 提交任务：沿用run/file_refs授权快照和工具预算；主Agent按需读取文档技能。
3. Agent调用既有builtin_read_material。工具准入核验所选file_id，查询该文件当前授权范围内的有效缓存。
4. 缓存命中：按定位/查询/offset/limit返回片段与来源。缓存复用不跳过授权。
5. 缓存未命中：读取授权原始blob并校验hash，启动无模型凭据的固定解析子进程；解析结果经大小/格式/hash复检后写回Backend缓存。
6. 模型依据实际读到的内容比较；报告工具发布新的MD/DOCX和来源。后续修改产生新file_id/父版本，不覆盖原件。
7. 运行详情显示正常工具过程；Langfuse展示实际Agent、模型和工具调用及耗时。

失败例：解析超时则终止真实子进程并返回明确工具错误，保留原件可下载；不能留下“永久处理中”，不能把失败缓存标READY，也不静默把二进制当文本读取。用户取消时停止该工具执行，既有已发布产物不伪称自动回滚。

## 6. 按需解析、缓存和预览的具体规则

### 6.1 固定解析执行

- 复用现有parse_document与解析库，不为同样格式重写第二套解析器；将CLI解析入口从常驻worker中分离为document_cli.py。
- 新增Runtime内部document_tools.py组织原始blob、提取、缓存与来源；materials.py和WorkspaceBackend调用同一入口。Backend不启动Python，也不承担Agent loop。
- 初版同时最多1个固定解析子进程、最多4个进程内等待者，等待不超过35秒；超出返回明确DOCUMENT_BUSY，不创建持久队列。事件循环继续处理SSE与取消。先不共享在途子进程，避免一个消费者取消导致其他任务被误杀；已完成缓存可以复用。
- 保留既有单文件5MiB、输出2MiB、35秒wall timeout、30秒CPU/512MiB子进程限制（Linux）和PDF/ZIP/XLSX边界。超时/取消后kill并wait，关闭管道和删除临时目录；失败不无限自动重试。解析子进程与Runtime共享容器总资源，实施时须核对并配置整体内存预算，不能把“独立进程”当成独立沙箱或删除现有资源保护。
- 子进程使用明确环境白名单，不继承模型Key、服务token或数据库配置；固定入口/参数不接受模型提供的任意shell命令。若Windows下无法提供同等资源限制，明确该运行方式的限制，不谎称等同Linux验收。

### 6.2 原始字节与文字视图

- `/inputs/<file_id>`仍是Agent读取的受控文字视图；受限执行器需要原始PDF/DOCX/XLSX时使用授权blob通道，并重新验证内容hash。
- 技能和脚本不能把虚拟/inputs路径直接当宿主文件路径；执行器用manifest映射到自己的临时输入目录。
- 检查框架download接口：不得把提取文字的UTF-8字节误标为原DOCX/PDF，不能靠改后缀冒充格式。

### 6.3 缓存

- 缓存按file_id、原始sha256、parser_revision识别。owner与run/file_refs每次读取都校验；不做跨用户仅凭hash命中的共享。
- 旧phase1-1结果在原hash/解析版本匹配时可继续复用；新解析器不能覆盖历史引用的定位依据。原始文件保持不变。
- 缓存结果采用唯一约束/比较后写入，重复请求不会产生互相覆盖的不同版本或重复正式产物；临时超时允许明确重试，永久不支持不伪装成功。
- 不把本地进行中任务当长期业务真相；进程重启可以重新按需提取，不恢复专用document_jobs租约循环。

### 6.4 资料预览

- GET `/api/files/{id}/parsed`只查询已有结果或“尚未提取”，不因GET产生计算。
- 用户点“提取并预览”时，新增受鉴权的POST入口（拟`/api/files/{id}/extract`），Backend检查文件归属，向Runtime固定解析入口传递有界原始字节与hash元数据，再保存结果。整个过程不创建Agent Run、不调用LLM。
- Agent工具读取与预览复用同一解析实现与缓存。内部传输使用二进制body与有界metadata，不为5MiB文件全局放大普通JSON接口限制。
- UI以“文件已保存 / 尚未提取 / 正在读取 / 可预览 / 无法读取”解释状态，不再让用户理解worker；取消/失败可重试，原件下载始终独立。
- 既有queued/processing状态仅在迁移兼容期读取，新路径不持续轮询一个不存在的后台任务。

## 7. 技能与工具扩展方式

保留已有tool_id和稳定输入输出；需要字段时先改schemas/样例/生成副本，再改Go/Python/TS。文档能力不另外建一套document Agent。

第一批只提供一个由项目维护的内置documents技能包：SKILL.md、references、输出模板；脚本先作为已注册固定工具的实现复用，不开放任意上传脚本自动执行。最初提示词只放名称、描述、只读路径与版本；匹配任务后由框架/文件工具读取正文。冻结包版本/hash，保证同一Run恢复不会读到突然变化的方法。

优先核对已锁定DeepAgents原生技能能力；用其可用机制接入，不能只为选择技能再调用一个模型或新建检索服务。WorkspaceBackend增加受控只读技能路径，写入/删除禁止；技能声明的工具不是权限来源，执行仍以Backend冻结快照为准。

已有用户技能的选择/数量/正文使用方式先保持兼容，后续再逐步包化；本轮不建市场、不批量导入外部技能、不追求完整插件平台。简单聊天不强制调用技能或展示计划。

## 8. Agent级Langfuse

- 复用本机已有Langfuse部署，恢复依赖后确认健康；为本个人Demo建立独立Project与专用Key，不复用公司数据/凭据。不增加第二套Langfuse部署。
- 根据本机Server和已锁定框架版本核对SDK并锁依赖，不盲抄公司版本或私有适配补丁。
- 官方CallbackHandler挂到graph执行配置，采集Agent、实际模型和工具子调用。一个run对应稳定trace，thread对应session，审批恢复仍关联同run，并给每次执行片段独立身份，避免并发串链。
- 主Run不是长时间悬挂的物理span；恢复可创建新的调用片段归入同trace。按现有业务事件解释终态，不人为制造模型调用或把审批中断标普通工具崩溃。
- 运行详情提供“查看Agent调用”链接，配置缺失则给出未启用状态；密钥只在Runtime部署环境，URL只来自服务端受控配置。
- 内容副本单独脱敏/限长，不直接导出env、token、完整原始文档或checkpoint；已授权材料的正文预览也受大小与权限约束。采用有界异步投递，SDK故障不会阻塞或改变Agent终态，关闭时执行有界flush。
- 不采集整个HTTP请求链、后台解析preview过程、排队/审批等待的独立全链路span或Python容器内部阶段；标准工具调用整体自然可见。暂不加入全套基础设施监控或评测平台。
- Langfuse配置或现有部署恢复有阻碍时，该Spec如实记依赖，不阻塞S16–S18文档改造；不以UI有链接冒充trace已写入。

## 10. 数据迁移与删除边界

1. 在独立验收项目先演练。记录当前镜像与同一时间点DB/files备份；日常5173不自动切换。
2. 协调迁移窗口暂停新增二进制上传与相关文档任务，用旧worker排空现有queued/processing任务；逐项记录无法完成的任务及明确失败结果，不伪造READY。
3. 非破坏性增加需要的缓存版本/唯一性与状态字段。已有parsed结果、source、原件、产物和版本链保留；document_jobs及旧schema表可留作历史，不在本轮DROP。
4. 同版本更新Backend/Runtime/Web，上传不再创建新document_jobs；Runtime统一走按需提取。先验证新路径后停旧worker，移除默认Compose服务及活动领取/回传接口，消除启动/脚本依赖。
5. 新版默认入口不保留长期双模式解析循环。兼容读取旧缓存不等于继续运行旧job系统；需要短期迁移代码时注明删除条件。
6. 若发布失败，先停止新增任务、处理在途执行与新数据，再按已验证兼容的旧镜像或同时间点DB+files恢复；新增状态/事件不能直接交旧消费者猜读。保留新版数据供核对，不重复写入。

必须从活动路径移除：document-worker常驻轮询、QueueDocument上传强制触发、claim/input/result解析job路由及新写入、UI“等待文档worker”文案、验收启动/重启对该服务的依赖。可保留的旧表/结果应明确只读历史用途，不把“Compose关闭”当成全部删除完成。

## 11. 验收矩阵与交付结果

| 检查 | 必须观察到的结果 |
